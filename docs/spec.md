# System Oneによる視力検査もどき

System One のモデルを使って、ランドルト環ベースの視力検査もどきのプログラムを作る。
対象はローカルの `clef` / `clef-flash` と、インターネット経由の `jev`（TypeSafe / OpenRouter）。

## プログラム構成

* ランドルト環の画像を生成する処理と、その画像を System One の API に投げて視覚検査をする処理に大別される
* プログラムはGUIを持つ。ウィンドウタイトルは「System Oneによる視力検査もどき」とする（`config.WINDOW_TITLE`）
* プログラム自体はオフラインで動作する（インターネット接続は不要）。**jev を選んだときだけ**インターネット接続を使う
* HTTP を扱うのは `services/` のクライアントだけに限定する（通信先は System One のエンドポイントのみ）。
  * `services/systemone.py`：クライアント共通（送信・認証ヘッダ・エラー処理・応答の解釈の入口）
  * `services/answers.py`：応答から回答を取り出す（API ごとの形の違いを吸収）
  * `services/clef_client.py` / `services/jev_client.py`：ローカル / インターネット経由の差分
  * `domain/questions.py`：方向判定の質問（言い回し・回答キーの変種）

## 技術要素

* Python。venvでグローバルな環境は汚さない
* OpenCV。画像生成に利用する
* Ollama。ローカルのLLM実行環境・APIサーバ
* clef / clef-flash。jev互換のSystem Oneのローカルモデル
* jev。TypeSafe のホストモデル（OpenRouter 経由でも同じ System One API を利用できる）

## clef環境

ローカルのOllamaで動作中。APIエンドポイントは以下。

`http://localhost:11434/v1/systemone`

* **本リポジトリにはサービスの実装もモデルの重みも含まれない。** 動かすには System One 互換の
  エンドポイントを用意するか、インターネット経由の `jev` を使う（`--models jev`）
* 判定させるモデル名は、エンドポイントが公開している名前を使う。名前や接続先は
  `--models <モデル名>` / `--base-url <URL>`（GUI は `config.CLEF_BASE_URL`）で変えられる
* 接続は**永続セッション（keep-alive）**で使い回す。また、ホスト名が `localhost` の場合は
  `127.0.0.1` に置き換えて接続する（Windows では `localhost` が先に IPv6(::1) へ接続を試み、
  Ollama が IPv4 のみを待ち受けるため約 2 秒待たされるのを避けるため）

利用できるモデルは以下の2つで、GUI のモデル選択で切り替える（後述の各リクエストの`model`に指定する）。

* `clef`：27B（Q4_K_M）。判定精度が高い。既定値
* `clef-flash`：9.1B（Q8_0）。高速だが判定精度が低い

後述のAPIエンドポイントの接続性の確認に利用するリクエストは以下で、応答のJSONのanswers.check_color.choiceの値が"red"のときは接続OK、それ以外のときはNGとする。

```
{
  "model": "clef",
  "state": {
    "text": "トマトやりんごは熟すと鮮やかな赤色になります。"
  },
  "questions": {
    "check_color": {
      "type": "choice",
      "instructions": "stateの内容から、説明されている物体のメインの色はどれですか？",
      "criteria": {
        "red": "赤色、またはそれに近い暖色",
        "blue": "青色、またはそれに近い冷色"
      }
    }
  }
}
```

## jev（TypeSafe の System One）を使う場合

`clef` は jev 互換のローカルモデルだが、jev 本体をインターネット越しに使うこともできる。

* 仕様: <https://docs.typesafe.ai/images>、<https://api.typesafe.ai/openapi.json>
* 接続先: `POST https://api.typesafe.ai/v1/systemone`（`config.JEV_BASE_URL`）
* 認証: `Authorization: Bearer <API キー>`。ヘッダ名と書式は `config.JEV_AUTH_HEADER` /
  `config.JEV_AUTH_SCHEME` で変えられる。キーは <https://console.typesafe.ai/keys> で発行する

### ローカルの clef との差分（`services/jev_client.py` が吸収する）

1. **画像の渡し方**: jev は画像を**トップレベルの `assets`** に置き（`{"<参照名>": {"type": "image",
   "format": "png"|"jpg", "data_base64": "<Base64>"}}`）、**その参照名が state / instructions /
   criteria のどこかに現れる**ことを要求する。本プログラムは state に `"image": "<参照名>"`
   （既定 `landolt`）を入れて満たす。ローカルの clef が使う `images: [Base64]` は jev には送らない
2. **Danger Zone ヘッダ**: 画像や Box 質問を含むリクエストには `TypeSafe-Danger-Zone-Images: true`
   が必要（無いと 400）。画像入りのリクエストにだけ付ける
3. **接続確認**: jev は `GET <接続先から /systemone を除いた URL>/models` でモデル一覧を取得できるので、
   これで認証と接続を確かめ、続けて System One へ小さなリクエストを 1 回送って応答の形まで確認する
   （ローカルの clef は色を答えさせる質問だけで確認する）。モデル一覧に `config.JEV_MODEL` が無いときは
   警告だけ出す
4. **通信**: インターネット経由なので環境のプロキシ設定（`trust_env`）を使う（ローカルの clef は使わない）。
   タイムアウトの既定は 180 秒
5. **モデル名**: `jev-latest` を既定にする（応答の `model` は `jev-1.13.0` のような実バージョン名）

応答の解釈は形の違いを吸収する。`answers.<質問キー>.choice` / `probabilities` / `confidence` を基本に、
`answer` / `value` / `result` / `choices[0].message.content`（JSON 文字列も可）/ トップレベルの `choice` も見る。
回答が方向の語（`up` / `右` / `west` など）なら質問のキーに寄せる（`neutral` などの質問の種類でも採点できる）。
確率が無い応答でも動く（確率は空で記録し、確信度は 0 になる）。

画像は PNG/JPEG で、長辺 1568px 以下に収める必要がある（本プログラムの画像は 640×640 の PNG なので
そのまま送れる）。

### OpenRouter 経由で使う場合

OpenRouter も TypeSafe 互換の SystemOne API を提供している（`POST https://openrouter.ai/api/v1/systemone`）。
**設定する場所は同じで、値だけを変える**（OpenRouter の公式ガイドも「base URL と API キーを変えるだけ」としている）。

* `JEV_BASE_URL`（既定）が `https://openrouter.ai/api/v1/systemone`。TypeSafe 直接にするときだけ
  `https://api.typesafe.ai/v1/systemone` を指定する
* API キーは同じ場所（`JEV_API_KEY` / `.jev_api_key`）に **OpenRouter のキー**を入れる。
  **環境変数がキーファイルより優先**なので、試した値が残っていないか
  `python scripts/show_jev_config.py` で確認できる（キーの値は表示しない）
* **画像は state を配列にして `image_url`（data URI）で渡す**。OpenRouter は TypeSafe の `assets` を
  受け付けず**無視する**ため（画像なしで処理され、ほぼ当てずっぽうの回答になる）。
  Danger Zone ヘッダは TypeSafe 直接のときだけ必要
* `--models jev` は選択名。リクエストの `model` には `JEV_MODEL`（既定 `jev-latest`）を送る
  （そのまま送ると `typesafe/jev` に解決されて 400 になる）。`typesafe/jev-1.13` のような
  API のモデル名を指定した場合はそのまま使う
* `JEV_MODEL` は `jev-latest` のままでよい。OpenRouter は素の System One のモデル名を
  `typesafe/` 名前空間へマップする（`jev-latest` → `~typesafe/jev-latest`、`jev-1.13` → `typesafe/jev-1.13`）。
  `typesafe/jev-1.13` のように接頭辞付きで指定してもそのまま使われる
* `config.JEV_PROVIDER` は接続先の URL から自動判定する（明示するなら `openrouter`）
* 違い: 課金は OpenRouter のアカウントに乗り、応答に `id` / `provider` / `usage.cost` が増える（読み飛ばす）。
  モデル一覧（`GET /v1/models`）は OpenRouter の名前空間なので**モデル名の照合は行わない**。
  画像入りの Danger Zone ヘッダは既定で送り、`config.JEV_SEND_DANGER_ZONE_HEADER` で外せる

### API キーの扱い（リポジトリに入れない）

* 環境変数 `JEV_API_KEY`（推奨。ファイルに残らない）
* または `config.JEV_API_KEY_FILE`（既定 `.jev_api_key`。1 行にキーだけを書く。`.gitignore` 済み）

未設定のときは通信せずに接続 NG を返し、設定先をログに出す（**キーの値そのものはログに出さない**）。
`scripts/check_tracked_info.py` が、追跡対象ファイルへの混入を検出する。

## ランドルト環の画像を生成する処理

* 生成する画像フォーマットはPNG
* 生成する画像のキャンバス全体のサイズは640*640で固定し、背景色は白固定
* ランドルト環の色は黒固定。ただし、後述の生成モードによるぼかしなどの結果でグレーになるのは許容
* ひとつのキャンバスに対して、ひとつのランドルト環を描画する
* ランドルト環のサイズは指定可能とするが、どのサイズでも環の中心がキャンバスの中心と一致するように置く
* ランドルト環のサイズは視力に対応付けて、高いほうから2.0, 1.5, 1.2, 1.0, 0.9, 0.8, 0.7, 0.6, 0.5, 0.4, 0.3, 0.2, 0.1とする。これらの視力値Vに対して、ランドルト環の外径サイズ（ピクセル）は52.7/Vとする
* ランドルト環の形状は国際基準（ISO 8596）に厳密に従う。すなわち、外径:内径:切れ目の幅 = 5:3:1
* 円環の輪郭は**画素の被覆率**（境界からの距離を 0..1 に均した値）で描いてアンチエイリアスする。2 値でラスタライズすると、環が小さいほど円のギザつきが目立つため。輪郭の 1px 以内だけが中間調になり、環の内部と背景は 2 値（黒・白）のまま
* 切れ目は「環の中心から指定方向へ放射状に伸びる、外径の 20% 幅の長方形」で片側だけをくり抜く
* 切れ目の空いている方向は上下左右の４つだけで、斜めは対象にしない
* 次の生成モードを持つ
  * 清明：デフォルトのクリアな状態
  * 近視：清明な画像をガウシアンブラー（cv2.GaussianBlur）でぼかしたロービジョンの模擬
  * 混濁：清明な画像を平滑化（cv2.boxFilter）＋コントラスト低下でぼかした水晶体の混濁の模擬
  * 乱視：清明な画像をカスタムのカーネルをcv2.filter2Dで作って特定の方向にだけぼかした乱視の模擬。方向は設定で調整可能
    * 既定の角度は 0°（水平方向のぼかし）なので、**上下の切れ目（縦のエッジ）の方が左右より強くぼける**。方向ごとの正答率を厳密に比較したいときは、この異方性を考慮すること（角度を 90° にする、方向ごとに 0°/90° を回す、などの対処が考えられる）
* 画像本体とは別に、その画像ではどの方向が開いているかを示す「正解」情報（up, down, left, right）も返す

## 画像をclefのAPIに投げて視覚検査をする処理

* ひとつのキャンバスの画像をclefのAPIに投げて、その結果を元にランドルト環のどこが開いているか回答し、正解と照合する
* clefへは「正解」情報は送らず、あくまで画像だけで判定させる
* clefへ送るリクエストボディのイメージは以下の通り

```
{
  "model": "clef",
  "images": [（キャンバス全体の画像をBase64エンコードした文字列）],
  "state": {
    "text": "視力検査用のランドルト環の画像"
  },
  "questions": {
    "landolt_c_direction": {
      "type": "choice",
      "instructions": "提示した画像のランドルト環の切れ目は、上下左右のどの方向に開いていますか？",
      "criteria": {
        "up": "上の部分が開いている",
        "down": "下の部分が開いている",
        "left": "左の部分が開いている",
        "right": "右の部分が開いている"
      }
    }
  }
}
```

* clefから帰ってくる応答のボディのイメージは以下の通り。このanswers.landolt_c_direction.choiceを回答として選ぶ

```
{
  "model": "clef",
  "answers": {
    "landolt_c_direction": {
      "type": "choice",
      "choice": "right",
      "probabilities": {
        "up": 0.0021,
        "down": 0.0114,
        "left": 0.0028,
        "right": 0.9837
      },
      "confidence": 0.9837
    }
  },
  "usage": {
    "input_tokens": 245,
    "output_tokens": 1
  }
}
```

* 回答と「正解」情報を比較し、正否を確定させる


## GUIの機能

* UI/UXはWindows 11の標準に従う
* ウィンドウ全体のサイズは可変
* デフォルトのウィンドウサイズは、本体部分の表示領域がキャンバス全体の原寸（640×640）と同じ大きさになり、キャンバスが1:1で表示されるようにする
* 画面左に操作用のパネルを作り、右側は本体部分
* 操作用パネル
  * 操作パネルは上から「検査開始」ボタン、モデル選択のドロップダウンリスト、生成モード選択のドロップダウンリスト、サンプル画像表示、生成モードの選択によって切り替わる設定値調整のエリアから成る
  * モデル選択のドロップダウンリストから使用するclefのモデルを選択可能。選択肢は `clef` と `clef-flash` で、デフォルトの選択肢は `clef`
    * 選択したモデルは[clef環境](#clef環境)のリクエストの`model`として、接続性の確認と検査の判定の両方に使う
    * 検査実行中はこのドロップダウンリストを無効化する
  * 生成モード選択のドロップダウンリストから生成モードを４つの中から選択可能。デフォルトの選択肢は清明
  * サンプル画像表示は、そのモードと設定値でサンプル生成したランドルト環の画像を表示する。このサンプルで空いている向きは右固定、サイズは左パネルの幅に適切に収まるように（サンプルに限ってキャンバス全体サイズは640*640未満でよい。このときは後述の視力値に寄らず、全体サイズに収まる限界の大きさで外径を決めて。ただし、アスペクト比は1:1で固定）
    * サンプル画像のサイズはウィンドウサイズに合わせて変わるが、再生成はせずに画像の拡大・縮小で対応する
  * 清明以外の場合は、各種フィルタの値を調整できるように設定値調整のエリアにスライダーを出す
    * スライダーは選択中の生成モードで実際に使うものだけを表示する（近視ならガウシアンブラーのカーネルサイズのみ、混濁ならboxFilterのカーネルサイズとコントラスト係数、乱視ならカーネルサイズ・方向・強度）
    * 各生成モードはそれぞれ独立した設定値を持ち、モードを切り替えるとそのモードで最後に使った値が復元される
    * 設定値のエリアの右上に、現在のモードの設定値をデフォルト値に戻すボタンを置く
  * 検査開始ボタンを押下したら、その生成モード・設定で検査を開始する
  * 検査開始ボタンは、検査実行中は「検査終了」ボタンとなり、押下するとその検査を終了する（検査の記録は保持せず、再開もしない）
  * 検査開始ボタンを押下した時点で、clefのAPIの接続性を確認して、接続不能な場合はモーダルダイアログで「clefのAPIエンドポイントが利用できません」と表示し、検査開始を中断する（本体部分の更新はしない）
    * 接続性のリクエストは[clef環境](#clef環境)で示したものを使う
    * モデルロードが必要な最初のリクエストは時間がかかる可能性があるので、この確認は2分のタイムアウトを持たせる。タイムアウトした場合は接続不能と判断する
    * 接続性の確認および検査中のclefへのリクエストはバックグラウンドスレッドで行い、待機中もGUIが操作可能な状態（メインスレッドをブロックしない）を保つ
* 本体部分
  * 本体部分は、検査中のランドルト環が描かれたキャンバス全体を表示するエリア。エリア上辺に半透明のオーバーレイで補助情報を表示するエリアを設ける
  * キャンバス全体の表示はアスペクト比を維持しつつ、ウィンドウサイズに合わせて伸縮・中央配置する
  * 検査実行中以外は白一色にする
  * 補助情報のエリアは、検査実行中および検査終了時に以下の情報を表示する
    * 1行目に、左から順に、使用しているclefのモデル、検査の画像生成モード、その右横にclefのAPIの応答速度（ミリ秒）
    * 2行目に、本体部分に表示している画像に対するclefの応答のパーセンテージの棒グラフ。棒グラフの横幅は本体部分の幅にフィットさせ（右端の棒が切れないようにする）、グラフは左から上・下・左・右の順に並べ、各棒に方向のラベルと値を表示する
    * 棒グラフは、clefが回答した方向の棒の外枠を太くし、そのラベルを太字にする
    * 本来の正解方向の棒の塗りとラベルは、正答だったならグリーン、誤答だったならレッドにする
  * 正否を示す中央のオーバーレイは設けない（正否は上記の棒グラフの外枠の太さと色分けで示す）
  * 検査終了時に視力値を示す本体部分の画面中央のオーバーレイは、以下のとおりとする
    * 枠は外側のひとつだけとし、二重の枠にしない（内側の文字には枠を描かない）
    * その大きさは中に表示する内容に依存せず固定とする
    * 文字列は、その固定した枠に沿うように、枠内に収まる最大の大きさで表示する
* 効果音
  * 正否判定の結果に応じて効果音を鳴らす
    * 正答のときは `sound/right` を再生する
    * 誤答のときは `sound/wrong` を再生する
  * 効果音のファイルはプロジェクト直下の `sound` フォルダに置く（拡張子は mp3 / wav / ogg に対応）。配置しなくてもアプリは動作する（無音になり、起動時に警告ログを出す）
  * 効果音の素材はアプリ全体で共通なので、以下の方針で扱う
    * 効果音のパス解決はアプリ全体で共有する単一のインスタンスに持たせる
    * 音の再生は1回ごとに新しい再生パイプライン（QMediaPlayer + QAudioOutput）を作り、終わったら破棄する。前回の再生のストリームやバッファを再利用しないため、前の音が次の音に混じることが原理的に起こらない
    * 同時に鳴るのは常に1つとし、新しい音を鳴らす前に前の再生を停止して破棄する
    * 再生が終わったら速やかに破棄し、次の判定のときには前の再生が残っていない状態にする
    * 検査の開始・終了・中断の区切りでも止めて破棄し、前の検査の音を持ち越さない
    * ループ再生はしない（1 回だけ鳴らす）
    * 音声の再生には Windows 用バックエンド（Media Foundation）を使う。Qt 既定の FFmpeg バックエンドは音声ファイルを開くたびに FFmpeg のログをターミナルへ出力し、読み込みにも 100ms 以上かかるため、環境変数 QT_MEDIA_BACKEND を Qt の初期化前に設定する（Windows 用プラグインが無い場合は FFmpeg のログだけを抑える）
    * 音声ファイルが存在しない場合や再生できない場合でもアプリの動作は止めない

* 検査は以下の流れで進む
  1. 視力値を下限の0.1とする
  2. 新しいキャンバスに視力値に対応する大きさのランドルト環画像を生成する
  3. 本体部分にキャンバス全体を表示する
  4. clefのAPIに投げて回答を出し、正否を決める。このとき正否に応じた効果音を鳴らす
  5. 本体部分上辺の情報を更新（clefの応答の棒グラフに、回答した棒の外枠の強調と、正解方向の棒の色分け（正答ならグリーン、誤答ならレッド）を反映）し、3秒間その表示状態を維持し、そのあと自動で次（以下の6か7）に進む。次に進む際にはその回のキャンバス画像はもう使わなくなるので、メモリ上に残り続けないように破棄する
  6. 正答だった場合、その視力値での累計誤答回数が0なら視力値を一段階上げて2に戻る。ただし、視力値がすでに上限値（2.0）だったときは検査を終了する。累計誤答回数が1以上なら、同じ視力値のまま2に戻る（もう一度検査）。
  7. 誤答だった場合、その視力値での累計誤答回数を1増やす。累計誤答回数が2になったら検査を終了する。同じ視力値のまま2に戻る（もう一度検査）。
  8. 検査を終了した時点で最後に正答した視力値をその検査で測定した視力値として確定させ、本体部分の画面中央に半透明オーバーレイで視力値を視力：(視力値)のフォーマットで表示する

## 統計バッチ（GUI を使わない自走プログラム）

GUI 版とは別に、モデル・モード・視力値ごとの正答率を比較するための自走バッチを持つ
（`src/systemone_vision_test/benchmark/`、起動は `python -m systemone_vision_test.benchmark`）。

* GUI のウィンドウや部品、効果音は一切使わない
* 画面表示が無いため、1 回の判定ごとの待ち時間は入れない（連続してリクエストする）
* `clef` / `clef-flash` / `jev` の 3 モデルについて、4 つの生成モードすべての測定を行う
  （jev はインターネット経由なので、既定の実行には接続先と API キーの設定が要る。
  ローカルだけで回すときは `--models clef clef-flash` を指定する）
* 清明以外のモードのパラメータは各モードの既定値を使う
* GUI 版のような正否に応じた視力値の段階的な変更は行わず、**全視力値 × 上下左右の各条件を 4 回ずつ**呈示する
* 正否を「モデル × モード × 視力値 × 開いている向き」で集計する（回答が得られなかった呈示は失敗として数え、分母に含める）
* 実行結果は Markdown のレポートとして出力し、**前提条件（各モードのパラメータ値）と結果の表**を載せる
* 方向ごとの正答率の偏り（回答ラベルの事前分布か、知覚の失敗か）を切り分けるため、質問の種類を変えて実行できる
  * 既定 / 回答キーを中立化（a/b/c/d）/ 日本語キー（上下左右）/ 説明の順序を逆に
  * 説明文を逆向きに（キーと説明が食い違う）/ 反対質問（切れ目が開いていない側を答える）
  * 回答キーを別語彙に（north/south/west/east、うえ/した/ひだり/みぎ）/ キーは同じで説明の対応だけをずらす / 補足文なし
* レポートには回答ラベルの分布・回答キーごとの平均確率・混同行列（提示した向き × 回答した向き）・
  確信度（最大確率）ごとの正答率を診断用に載せる（低確信の呈示を「判定不能」として切り分けられる）
* 呈示ごとの生データ（JSON）も出力し、後から再集計できるようにする
* まとまり（モデル × モード）ごとに途中経過を保存し、中断しても続きから再開できる（実行条件が前回と違う場合は再開せず、最初から実行し直す）
